# Frame identity and publication primitive

The CPU command's PNG resume uses this package through the compositor's owned execution snapshot. The experimental GPU command does not use it and refuses PNG resume. This package alone cannot discover omitted dependencies or prove that a renderer consumed the bytes hashed by Build. Callers must enumerate every actual named dependency, including score, cues, optional passes and selected fire frames, and render from the same immutable input snapshot. A mutable input changed after Build requires rebuilding the key; file timestamps are not a substitute. Build detects ordinary changes during hashing, not adversarial same-size rewrites with restored timestamps.

## Identity

Build accepts a Spec containing the executable path, deterministic render-settings bytes, named Input paths and selection Choice strings, FPS, absolute nonnegative frame index, dimensions, device and backend. Every supplied file is read and SHA-256 hashed. A key also binds the exact names and choices, so two fire choices with identical bytes can still differ. Inputs should use stable logical names such as fire.steady, fire.swell and fire.burst, with the selected sequence/frame in Choice. Multiple contributing fire frames need distinct names.

Settings must represent all effective rendering settings, with deterministic serialization; do not include stretch start/end or output paths. There is deliberately no job-range field. Equal absolute frames with equal effective specifications have equal keys across overlapping jobs. File locations and mtimes do not enter the key, allowing identical immutable inputs at different farm paths. Binary bytes, settings bytes and every supplied input's bytes do enter the key. Device/backend are caller-supplied exact identities, not automatically discovered capabilities.

Build rejects missing/nonregular inputs and final-component symlinks. Ancestor symlinks are resolved to support platform temporary directories. Paths and raw settings are never persisted in manifests. Input errors suppress filesystem paths; logical input names should not contain secrets.

## Store protocol

Open requires an existing trusted local output directory. Keep its ancestors and contents protected from uncooperative writers. Store anchors file operations with os.Root and checks the directory handle identity. Use Close when finished. This implementation requires Unix directory flock, atomic hard links of symlink inodes, atomic rename and working file/directory fsync semantics; unsupported filesystems fail rather than silently downgrade. Distributed/network filesystem semantics have not been validated.

Publish(key, pngBytes, false) checks the encoded size before cloning and serializes cloning, validation and decoding under the store mutex and directory flock. Encoded input is limited to 128 MiB; dimensions are bounded to a worst-case 128 MiB decoded image at eight bytes per pixel, allowing 4096 by 2160 16-bit RGBA. PNG acceptance deliberately uses a narrow subset: noninterlaced grayscale, grayscale-alpha, RGB or RGBA with only IHDR, contiguous IDAT and IEND chunks. Palette, transparency chunks, all ancillary chunks, unknown critical chunks and interlacing are rejected, including otherwise-valid PNGs outside this subset. Validation checks CRCs, exact chunk ordering, a single complete zlib stream, exact decompressed scanline length, filters, final IEND and absence of trailing bytes, followed by the standard PNG decoder. Separate Store handles cooperate, including overlapping jobs. With a valid existing exact key it returns reused=true without replacing pixels. A different key returns ErrConflict; malformed, missing-component or digest-mismatched committed state returns ErrCorrupt. Neither condition is silently reused or overwritten. Verify returns verified PNG bytes, not a pathname that must be reopened later.

Publication writes private exclusive files into a random 0700 generation directory, synchronizes both the complete PNG and its manifest, and synchronizes the generation directory. The manifest binds the exact key, absolute frame, dimensions, PNG byte count and SHA-256 of the entire PNG. A private .generation-<id>.link symlink points directly to .generation-<id>/frame.png. Its directory entry is synchronized before installation. One atomic no-clobber hard link of that symlink inode creates the flat frame slot only after the pair is complete. The flat entry is a single relative symlink, not a chain of symlinks. The retained private link is an ownership witness: verification and redraw require the flat entry and witness to be the same symlink inode. Merely copying a link target, even one naming a valid generation, does not establish ownership. Readers select the PNG and metadata through the same generation pointer, never through independently replaced sibling files. A directory synchronization completes publication. Verify and verified Publish reuse synchronize the output directory before reporting success, so a retry after a failed final directory synchronization must attempt that durability barrier again. A sync error after pointer installation is an uncertain outcome: retry with Verify, never assume the slot is absent. Physical power-failure behavior and injected synchronization failures have not been tested.

Publish(key, pngBytes, true) is an explicit destructive redraw, not resume. It atomically replaces an owned generation pointer under the same writer lock, including when the previous key differs or the previous generation state is corrupt. A temporary hard link of the new witness is renamed over the owned flat entry. If the slot is absent, even explicit redraw uses no-clobber installation. A preexisting regular file, directory or unbound symlink is refused with ErrCorrupt in both modes; redraw never authorizes replacing arbitrary user output. The old generation and its witness remain immutable. Two explicit redraws are serialized and the last successful one wins; redraw must not be enabled merely because Verify reported a conflict. Existing directories at frame-slot names are not removed.

Frame slots use %05d.png: absolute frame 17 is 00017.png, and frame 100000 is 100000.png. Each points directly to .generation-<id>/frame.png, so ordinary PNG readers can open the flat filename. Verify resolves that pointer once and checks the sibling manifest in the same generation. This is an on-disk layout compatibility change from frame-%012d directory pointers; manifest version 1 and identity keys are unchanged. Legacy frame-000000000017 slots are ignored, never reused, migrated, replaced or deleted; a new flat slot may be published alongside them. Flat files or symlinks from other producers are not adopted. Ownership relies on retained symlink hard links; copies or archives that do not preserve their shared inode are refused. The CPU command uses this layout through its owned execution snapshot; the GPU path does not.

## Interruption and limitations

A crash before slot installation leaves an unreferenced generation, never a reusable frame. A crash during pointer replacement exposes either the previous complete generation or the new complete generation under filesystem atomic-rename guarantees. An absent slot can be published normally; an owned dangling/incomplete slot is rejected and requires explicit redraw. A dangling/incomplete slot without a matching ownership witness is refused even for redraw. There is no persistent lock file to become stale. A dead process releases its flock. Old generations, ownership witnesses and interrupted private files are intentionally retained; automatic garbage collection could race readers and is outside this primitive.

Verification checks content integrity and identity binding, not authenticity against malicious writers who can rewrite both manifest and pixels. All participating publishers must use this protocol. Directory flock serializes different frame slots too, favoring simple correctness over throughput; rendering happens outside the lock, but PNG validation and decoding are serialized under it. Input enumeration and immutable render snapshots remain caller responsibilities; the CPU command supplies its owned execution snapshot. Remote-filesystem qualification and generation garbage collection are not implemented.

Tests use synthetic PNGs and temporary directories, including a generated 4096 by 2160 16-bit RGBA image to verify the decoded allocation budget. They exercise identity sensitivity, map/location independence, two independent Store writers, same/different identity races, strict PNG validation, corruption rejection, explicit redraw, interrupted generations, private permissions and unsafe slots. They model crash-visible states; they do not inject physical power failures or run rendering. A parent-directory replacement test verifies that publication stays in the originally opened output directory rather than following a substituted ancestor symlink.

PublishContext adds cancellation to publication. Both the in-process mutex wait and the nonblocking directory-flock polling wait honor context cancellation. Context is retained through validation and generation staging, checked after expensive validation and immediately before installing or replacing the publication pointer. Cancellation before that final check leaves no installed slot; staged files are cleaned up. PNG decoding and fsync themselves are not interruptible. Cancellation can race the atomic commit syscall after the final check: once installed, the pointer is not rolled back, and the final directory sync still runs to establish durability. Publish is the background-context convenience wrapper. Context wait tests cover both separate Store handles and contention on the same Store; deterministic cancellation injection between staging and the commit syscall is not tested.
