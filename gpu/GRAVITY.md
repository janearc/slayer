# Metal gravity work

The prototype is integrated with the RC in `feat/sextant-throughput`.
Branch/workspace paths and measurements below retain their original
prototype context; they are not setup instructions for a fresh clone.

What is called Celestial's `hole.MetalLibrary` below is Slayer's
`metal.GeodesicLibrary` since 2026-11-14: the same shader, kept in
Slayer's `metal` package, with Celestial v0.0.9 used as released.

This branch tests Celestial's new `hole.MetalLibrary` on Metal against
`Hole.Step`. Celestial owns the Kerr equations and RK4 integration; Slayer
owns GPU dispatch and scene transport. No physics code is copied into
Carrie. The workspace imports these owning implementations directly.

The adapter supports one placed field, CPU observer seeds, GPU integration,
escape and re-entry. It tests intersections along curved segments and
applies circular-emitter frequency shifts and outside-field Doppler boosts.

Smooth disc geometry stays analytic. A radial light table is
generated by the existing Thin texture; streaks use Slayer's Metal noise.
Axial beams and multiple fields remain unsupported.

The initial complete scene comparison passed with mean relative light
error 0.0000432, largest 0.0204, and no coverage or depth mismatches.
Disc depth mismatches were repaired by resetting local opacity on each
re-entry.

The radial table passes at mean error 0.0000631 and largest
0.001185.

Moving close-ups at zero and two seconds pass with mean errors
0.000176 and 0.000166, and no coverage or depth mismatches. More than
100 of the 1,536 pixels change between those frames.

Compensated RK4 updates removed two captured-depth mismatches without
changing the original depth tolerance. Position and momentum additions
retain their rounding residuals between steps and reset on re-entry.

Mass-normalized integration avoids astronomical values in metric powers.
The field adapter's Go statements are fully covered, including injected
encoding, baking, compilation and dispatch failures and kernel cleanup.

This is not a claim of full coverage for the existing GPU package.

The tests cover zero and positive spin, non-equatorial rays, backward
tracing, a 1,024-step photon orbit, and the oblate coordinate disc. The
ordinary step tolerance is 0.0003 relative to at least one.

The critical trajectory allows 0.003. These are chosen comparison bounds,
not statements about the accuracy of an eventual photon-ring image.

The disc boundary test exposed float cancellation: Metal reported a time
of -978.1343 where the CPU returned 0.01. An explicit equatorial-disc
radius branch prevents the tiny false radius and the resulting force.
The counterexamples remove gravity, spin, integration and that guard.

On this M3 Max, 4,096 integrations of 256 fixed steps took 226–243 ms on
CPU and 8.8–10.6 ms through Metal, in three one-iteration measurements.
Compilation is outside the timed section. Metal timing includes the
dispatch and readback. Each invocation reports one component.

Both sides perform the same count of integrations. This measures stepping
throughput. It does not measure frame rate, radiative transfer, or
near-critical adaptive integration.

Harness comparisons and actual frame benchmarks cover the supported
single-field background path.

The current dispatch band is sixteen rows, to bound latency
near critical rays. GPU transport reads the reference stopping policy
through trace.FieldSettings and Celestial's shader pacing parameters.

The total GPU step budget is bounded; compare long winding paths before
claiming resolved photon subrings. Mirror paths through gravity still
need explicit validation. The receipts below cover the configured background.

The original runs used Slayer's `feat/metal-gravity` and Celestial's
`feat/metal-geodesics` from a shared workspace. The named checks and
benchmark in those branches were prototype runs.

The dispatch comparison checks identical samples at 2, 8, 16 and 32 rows,
including a partial final band. On this M3 Max, the controlled close-up's
GPU time fell from 226 ms at two rows to 42 ms at sixteen. Larger batches
did not improve its device time further.

Renderer instances retain one immutable observer-seed tape for stationary
cameras. The key includes dimensions, camera, field placement and physics,
observer velocity, and lens state. Ordinary custom lenses remain uncached;
an optional film.IdentifiedSensor supplies an explicit changing RayKey.

Host tests prove reuse, invalidation, and preservation of older tapes.
Four compiled cache counterexamples reject missing reuse and stale keys.
Moving-disc comparisons continue to match the CPU with cached seeds.
LastTiming reports stage durations and whether the tape was reused.

The full bright 480×319 Carrie scene now measures 147 ms for a warm frame,
against 15.7 seconds on CPU, about 107 times faster. The measured frame
uses one ray per pixel, Vaporwave, full opacity and the held photon zoom.
This is frame-production time, not measured live GUI frame rate.
